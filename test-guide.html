Resumen ejecutivo

  • Los enlaces de acceso por correo fallaban para cualquiera con correo corporativo, porque el antivirus de correo abre el enlace antes que la persona y lo gasta.
  • A1 añade una página intermedia, /login/confirm, que no canjea nada hasta que alguien pulsa un botón. Un escáner que abra la página se encuentra HTML inerte.
  • A2 añade acceso con contraseña junto al enlace mágico, que sigue funcionando. La contraseña se ofrece, nunca se obliga.
  • A3 añade recuperación de contraseña, que se apoya en la misma página de confirmación.
  • La suite automática pasa de 24 a 47 pruebas, todas en verde.
  • Importante El código por sí solo no arregla nada: hay que editar tres plantillas de correo en Supabase. Sin ese paso, producción sigue igual y las pruebas automáticas igualmente pasan.

Contexto: qué había antes

El único modo de entrar era el enlace mágico. /login pedía un correo, Supabase enviaba un mensaje con un enlace, y ese enlace apuntaba directamente a la URL de verificación de Supabase.

Esa URL es un GET que gasta un token de un solo uso. No había página intermedia, ni contraseña, ni forma de recuperar nada.

Problema

Microsoft Defender para Office 365, igual que Proofpoint o Mimecast, abre los enlaces del correo entrante para analizarlos antes de entregarlo. Al abrirlo, consume el token. Cuando la persona hace clic, Supabase responde otp_expired: "Email link is invalid or has expired".

Evidencia del 16 de septiembre de 2026. El mismo enlace enviado a @raptns.com (Microsoft 365) falló, y enviado a @rapqa.com (Mailgun, sin escáner) funcionó. El DNS confirma la diferencia: raptns.com tiene MX hacia outlook.com, rapqa.com hacia mailgun.org.

Esto afecta directamente al cliente: su cuenta es dwright@raptns.com, el mismo dominio con el mismo escáner.

  • Tres plantillas de correo en Supabase: Magic Link, Confirm signup, Reset Password.
  • Añadir /login/confirm a las Redirect URLs.
  • Dejar desactivado "Require current password when changing password".
  • Bajar "Email OTP expiration" a 900 segundos.

Cómo se resolvió

A1: la página espera a una persona

El correo deja de enlazar a Supabase y enlaza a thedesignerplan.com/login/confirm, llevando el token en la URL. La página lo lee, limpia la URL, y no hace nada más. El canje ocurre solo dentro del manejador del clic. Un escáner abre la página, no pulsa botones, y se va.

Cuatro decisiones que sostienen esa propiedad:

  • Nada canjea fuera del clic. Sin temporizadores, sin canje al cargar.
  • El type se lee de la URL, nunca se fija en el código. Supabase manda "Confirm signup" a un correo nuevo y "Magic Link" a uno existente, con tipos distintos. Fijar uno rompería el otro.
  • La URL se limpia al cargar, no después de canjear, para que el token no viva en la barra de direcciones mientras la persona lee.
  • El next es una ruta del sitio, nunca una URL. Una URL sería una redirección abierta, y un valor javascript: entregaría la sesión.

A2: contraseña, sin quitar el enlace

Un solo mensaje de error para todo, a propósito. Supabase devuelve el mismo Invalid login credentials para contraseña incorrecta, para cuenta sin contraseña y para correo inexistente, y documenta que no se pueden distinguir. Ramificar la interfaz según eso filtraría qué correos tienen cuenta.

La contraseña se fija desde /dashboard/profile, en un formulario separado. No es cosmético: el formulario de perfil se serializa con FormData y se envía a una función de Netlify, así que un campo de contraseña dentro acabaría en los logs de esa función.

Tras fijarla se cierran las demás sesiones (signOut({ scope: 'others' })). Sin eso, quien encuentre una sesión abierta en un ordenador compartido podría ponerle contraseña y quedarse con la cuenta para siempre.

A3: recuperación heredada

El correo de recuperación es también un enlace de un solo uso, así que se enruta por la misma página. Tres de las cinco pruebas de A3 pasaron antes de escribir una línea de A3.

Notas, riesgos y pendientes

Riesgo aceptado

Un escáner que ejecutara JavaScript y pulsara botones seguiría gastando el token. Defender no hace eso, y Supabase documenta esta página como la mitigación, pero no es una garantía. La contraseña de A2 es la alternativa para quien se viera afectado.

Si llegara a ocurrir, el siguiente paso está documentado en la especificación: añadir {{ .Token }} a las plantillas y un campo de código de seis dígitos. Un escáner puede leer un código, pero no gastarlo. No se ha construido porque no hay evidencia de que haga falta, y sería una segunda pantalla que mantener.

Lo que las pruebas automáticas no cubren

  • Importante Que las plantillas se hayan cambiado. Las pruebas acuñan sus propios tokens y construyen la URL ellas mismas, así que pasan igual aunque Supabase siga mandando el enlace viejo. Es el punto ciego mayor de esta entrega, y por eso los pasos 7 a 9 son manuales y obligatorios.
  • El comportamiento real de Defender. La prueba E.2 simula un escáner con una petición sin JavaScript, que es el modelo correcto, pero no es el producto real.
  • Las cabeceras de seguridad servidas. netlify dev con --dir usa un servidor estático simple que ignora _headers. La prueba E.9 comprueba que las reglas están declaradas en el archivo; que se sirvan se verifica en el paso 21.
  • Caducidad real del token. Se sustituye por un token ya gastado, que produce el mismo error.
  • Entregabilidad y aspecto del correo en Outlook de escritorio, web, Gmail y iOS.

Decisiones que conviene conocer

  • El mínimo de contraseña son 6 caracteres, por decisión explícita de Adrian: "no compliquemos esto, esto tampoco es una cosa bancaria".
  • El enlace mágico no desaparece. Se mantiene porque mucha gente prefiere no recordar contraseñas.
  • La contraseña se ofrece, no se obliga.
  • Inferido Esto deroga una línea del PRD. docs/dashboard-onboarding-plan.md:108 decía que la contraseña se introducía solo al comprometerse con Stripe, como señal de "esto ya es una cuenta con dinero". La decisión de Doug del 28 de mayo la sustituyó. Queda anotado en la especificación.
