Decision summary

Lectura 2 adoptada. El formulario /partner-apply sobrevive como enrichment opcional post-login, no como gate. Account creation = SIEMPRE magic-link. Stripe Connect = único gate de comisión. El form solo agrega datos a una row que ya existe en partners.

Invariants (no se rompen)

⚠ Si cualquiera de estos se rompe, el form se vuelve un gate disfrazado

  • Account creation = SIEMPRE magic-link. El form NUNCA crea cuentas.
  • Form backend = UPDATE, no INSERT. Falla con 401 si no hay row preexistente.
  • Todos los campos opcionales. Cero required. Submit con form vacío funciona.
  • El form vive dentro del dashboard, no en /partner-apply como entry point.
  • "Apply to the program" muere como frase. CTAs se renombran a "Get started" / "Log in".
  • El form es removible en <30 min sin romper nada más del sistema.

Decisions log

  • 2026-05-21 Adoptada Lectura 2 sobre Lectura 1. El form sobrevive como enrichment opcional post-login. Razón: PRD docs/dashboard-onboarding-plan.md:150 ya anticipaba "optional, presented at setup, skippable" profiling. Pivot cost si Doug objeta = ~30min.
  • 2026-05-21 Decidido no preguntar a Doug ex-ante. Su veto en el meeting fue contra el gate (mandatory upfront), no contra captura de datos opcional. El costo de pivot es bajo y el costo de idle waiting es alto.

Open questions

  • ¿Slim-down del form? Hoy pide state, ZIP, address, project size, clients/año, 7 categorías, contact method, free-text. Aun siendo opcional, es intimidante. Posible slim a: categorías + project size + clients/año. El resto a futuro cuando haya use case.
  • ¿Cómo se integra con el admin dashboard de Doug? Doug está construyendo un sales CRM en paralelo. Los datos del form (specializes_in, etc.) serán visibles para sales agents. Hay que coordinar el shape final.
  • ¿Backfill de partner rows existentes? Si hay leads pre-existentes en leads sin partners row, ¿qué pasa cuando se loggean? Decidir: ¿se merge la row de leads + se crea partner? ¿O leads y partners se mantienen separados?
