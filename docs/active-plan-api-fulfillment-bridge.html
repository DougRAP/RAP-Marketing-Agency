Decision summary

Reuse the existing Spring Boot engine, expose it via 4 JSON endpoints. Browser → Netlify Function (BFF) → Spring Boot via HMAC-SHA256 signed requests. Spring Boot handles payment, plan numbers, SOAR writes, commission ledger. Supabase keeps marketing/dashboard data + a writeback cache of plan_number. No user JWT crosses into the engine. The browser never talks to the engine directly.

Invariants (no se rompen)

⚠ Money rules · auth rules · data flow rules

  • Spring Boot = canonical source for money. Plan numbers, commission ledger, payouts. Never duplicated in Supabase.
  • Supabase = canonical source for marketing/auth. Leads, partners (identity), dashboard data, plan_number cache.
  • HMAC secret never in client JS. Lives in Netlify env vars + Spring Boot env vars only.
  • User JWT never crosses into Spring Boot. Netlify Function validates JWT, then talks to engine using its own HMAC identity.
  • Stripe Connect onboarding return URL points to thedesignerplan.com, NOT designerplan.io anymore.
  • The Spring Boot continues to serve designerplan.io until cutover (we don't break the old site).
  • All money writes are idempotent. Stripe webhook may fire twice — engine handles dedup.

Decisions log

  • 2026-05-21 Reuse engine, expose via JSON endpoints behind HMAC. No rewrite of Spring Boot business logic. Browser → Netlify Function (BFF) → Spring Boot. Validated in the architecture proposal + the 5/21 meeting with Doug.
  • 2026-05-21 Supabase is the only DB the new site touches directly. Engine writes back plan_number to Supabase after each successful payment. No cross-DB queries from the site.
  • 2026-05-21 Single-plan slide-out, no shopping cart. >99% of historical purchases are single-plan; cart adds friction without value (per architecture proposal §3).
  • 2026-05-22 Q1 — HMAC: start with one key pair. Netlify ↔ Spring Boot uses a single shared secret. Multi-key rotation is a future enhancement; not needed for go-live. Affects Wave A.2.
  • 2026-05-22 Q2 — Adrian has both required access points. Push to the Designers Bitbucket repo + SSH to Rackspace Tomcat. Wave B is unblocked.
  • 2026-05-22 Q3 — Stripe live-keys flip: deferred. Decide closer to go-live based on smoke-test readiness. All Wave A–D work uses Stripe test mode. Re-evaluate at Wave E.17.
  • 2026-05-22 Q4 — Dashboard cache TTL: deferred. Decide at Wave C.12 (implementing the BFF). Default proposal stays 30s; revisit then.
  • 2026-05-22 Q5 — Promotions IN for 2026-06-01, scheduled last. Promo A (first-plan-on-us) and Promo B (refer-a-designer) are part of go-live. Moved to new Wave F appended after Wave E so they don't block the core fulfillment flow.
