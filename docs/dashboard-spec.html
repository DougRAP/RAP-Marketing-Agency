3 · El puente Supabase ↔ SOAR — resuelto (lookup por email)

Enfoque: el usuario se loguea en Supabase (email). El BFF valida el JWT y pasa el email verificado al engine (firmado HMAC). El engine busca el Dealer por email — DealerRepository ya tiene findBydealerEmail() y findBykeyEmail() — y devuelve la data del dashboard. En el primer login exitoso, cacheamos el soar_dealer_id en la fila partners para no repetir el lookup.

⚠ Riesgo: si el email de signup ≠ el email del Dealer en SOAR, el lookup falla. Mitigación: probar contra dealerEmail y keyEmail, y empty-state claro si no matchea. (Adrian verifica contra SOAR.)

5 · Tema aparte y grande: ¿cómo se entrega el plan? (fulfillment)

Hallazgo al revisar el código: hoy el plan no se registra automáticamente al pagar. El flujo actual es: pago exitoso → el cliente es redirigido a un formulario /registerPlan donde se ingresan datos (sales order, dirección, fotos) y ahí se genera el warrantyNumber (plan_number) vía un stored procedure de SOAR. Ese flujo está pegado a la sesión HTTP del sitio viejo.

En el modelo nuevo (slide-out + Stripe Elements, sin ese formulario y sin sesión), el plan no se registraría solo. El webhook de pago hoy solo actualiza el estado de la transacción — no crea el plan ni genera el plan_number.

Modelo acordado (Adrian + Doug)

El slide-out de Doug recoge, al momento del checkout: datos del cliente + sales order number + recibo (upload) + cuál de los 3 planes (el card elegido). Es decir, todo lo que el registro necesita viene del frontend. Separación limpia:

DatoOrigenPara qué
amount_centspágina (flat-% del retail)precio que se cobra
plan_id (1 de 3)página (el card)qué plan registrar
cliente + sales_order_number + recibopágina (slide-out)registro en SoarSales

Flujo de fulfillment que construiremos

  1. Checkout: el engine crea el PaymentIntent y persiste los datos de registro (plan_id, cliente, sales_order) en la metadata del PI. El recibo-archivo va a un endpoint de storage aparte, casado luego al plan_number.
  2. Pago: Stripe confirma.
  3. Webhook payment_intent.succeeded: lee la metadata, llama al servicio de registro (genera warrantyNumber vía el stored procedure de SOAR, crea la fila SoarSales, registra la comisión) — idempotente. Acto seguido escribe la venta a Supabase (con el plan_number ya existente).

Esto requiere desacoplar la lógica de registro del formulario /registerPlan con sesión y volverla un servicio stateless invocable desde el webhook. Es nuestro lado (engine), no depende de la página de Doug — lo planificamos aparte porque toca código de dinero + dedup.
